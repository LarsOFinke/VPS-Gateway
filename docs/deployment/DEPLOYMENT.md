# Deployment

## Target selection

Every public command defaults to test. Production must be stated explicitly:

```bash
./scripts/setup                         # local test
./scripts/setup --production            # local production
./deploy.sh                             # remote test
./deploy.sh --production                # remote production
./update.sh --production                # production update
```

Runtime profiles are `.env.test` and `.env.production`; origin SSH profiles are
`.env.origin.test` and `.env.origin.production`. All are private mode-0600 files.
The loaders reject a target/profile mismatch and reject combined target flags.

## Local or target-side setup

`scripts/setup` creates a target-specific runtime profile from
`infrastructure/.env.<target>.example`, generates the API token, creates the
target-specific external Docker-internal network, verifies that an existing
network is also internal, builds the gateway, and runs its health check.
When it first initializes admin authentication, setup prints a random bootstrap
password once. Capture it without recording it in shared deployment logs and
rotate it immediately in the loopback admin panel.
Review the email and ports before using `connect-route`.

Test uses non-privileged 18080/18443 host ports and Let's Encrypt staging by
default. Production owns 80/443 and the production ACME endpoint. Do not start
production until any existing listener on those ports has been included in a
controlled cutover window.

When upgrading an earlier installation, confirm every stored upstream already
uses a single alias such as `app-gateway`; IP-based or dotted upstreams will be
rejected. An existing non-internal ingress network must be drained and recreated
by `scripts/setup` before activation.

## Origin-to-server deployment

Every immutable release needs a higher synchronized SemVer:

```bash
./set-version.sh patch
./set-version.sh minor
./set-version.sh 1.0.0
```

Configure each target independently:

```bash
./deploy.sh --configure
./deploy.sh --production --configure
```

SSH identities and Ed25519 release signing keys remain outside the repository.
The remote account receives narrowly scoped sudo permission only for a root-owned
runner. Deployment signs the checksum, transfers artifact, checksum, and
signature to the configured stage, then the runner validates signature, caller,
ownership, target, paths, and filenames before invoking the root-owned installer.

Provision that boundary once from an existing server administrator account:

```bash
sudo infrastructure/scripts/release/provision-deploy-user.sh \
  gateway-admin /tmp/gateway-admin.pub /tmp/release-signing-key.pub.pem
```

The SSH public key is the deployment identity's public key. The release public
key is generated by `deploy.sh --configure` next to the private signing key. Copy
only those public files to the server for provisioning. The release then activates
under:

```text
/srv/vps-gateway[-test]/
  current -> releases/<version>
  releases/
  shared/.env
```

On a fresh server, the first deployment initializes `shared/.env` with a random
token and stops before activation. Review that file on the target and rerun. A
failed subsequent activation restores the preceding `current` release and
requires its startup to succeed. A failed first activation explicitly stops the
new Compose project. Rollback failure is reported as a critical manual-recovery
condition. Every deployed release needs a new SemVer in `VERSION`.

## Route onboarding

Use `docs/ROUTE_INTEGRATION.md` to adapt the upstream first. Then rehearse
DNS, routing, headers, and ACME against test before applying production:

```bash
./scripts/connect-route --test app-test app-test.example.net http://app-test-gateway:8080
./scripts/connect-route --production app app.example.net http://app-gateway:8080
```
